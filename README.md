# upland

Upland is a Rust web application: an [axum](https://github.com/tokio-rs/axum) HTTP JSON API that also serves an embedded React single-page app (Vite, in `web/`). One binary serves both.

## Install

```sh
brew tap xminihub/tap
brew install upland
brew services start upland   # http://127.0.0.1:8310
```

`brew services stop upland` stops it; `upland` on its own runs in the foreground. The formula lives in [`xminihub/homebrew-tap`](https://github.com/xminihub/homebrew-tap) and is generated by a release, never edited by hand. Release assets can also be downloaded from a [release](https://github.com/xminihub/upland/releases) and run directly.

## Running

```
upland [OPTIONS]

      --host <host>     Bind address (default 127.0.0.1)
      --port <port>     Listen port (default 8080)
      --db-path <path>  Database file (default: a per-user data directory)
  -V, --version         Print the version
  -h, --help            Print this help
```

`UPLAND_HOST`, `UPLAND_PORT` and `UPLAND_DB_PATH` set defaults for the three flags; the flags win. upland binds loopback unless told otherwise, so reaching it from another machine is a choice you make in the invocation, in a service unit or in a container's args (ADR-0002).

## Database

Upland persists to a single embedded SQLite file through SQLx (ADR-0003): one writer connection plus a read pool, WAL, and migrations embedded from `migrations/` and applied at startup. Its location is the **database path**: `--db-path` or `UPLAND_DB_PATH`, defaulting to the platform's per-user data directory (macOS `~/Library/Application Support/upland/upland.db`, Linux `$XDG_DATA_HOME` or `~/.local/share/upland/upland.db`, Windows `%APPDATA%\upland\upland.db`). The database opens before the port binds; a path that cannot be written is a startup error, not a fallback.

Queries are compile-time-checked SQLx macros against committed offline metadata (`.sqlx/`, `SQLX_OFFLINE=true` in `.env`), so builds and tests need no database service. After adding a query or a migration, regenerate the metadata locally:

```sh
cargo install sqlx-cli --no-default-features --features sqlite   # first time
cargo sqlx prepare                                               # after changes
```

## Endpoints

- `GET /api/v1/hello` — hello message
- `GET /healthz` — health check
- `GET /` — single-page app (served from `web/dist`, embedded into the binary in release builds; when `web/dist` is empty the SPA routes are not mounted and the API works alone)

## Development

Backend:

```sh
cargo run             # start the server on 127.0.0.1:8080 (default per-user database path)
cargo run -- --db-path ./upland.db   # a repo-local database for tinkering
cargo test --locked   # unit tests + HTTP integration tests (axum-test, in-process)
cargo fmt --check     # format
cargo clippy --locked --all-targets  # lints (CI denies warnings)
```

Frontend (Bun, in `web/`):

```sh
cd web
bun install           # install dependencies (bun.lock committed)
bun run dev           # Vite dev server on :5173, proxies /api to 127.0.0.1:8080
bun run build         # typecheck + production build into web/dist (embedded by cargo build --release)
bun run lint          # oxlint
bun run test          # Vitest (jsdom, app-root seam)
bun run format:check  # Prettier check (CI enforces; bun run format to fix)
```

For full-stack development run `cargo run` and `bun run dev` side by side and open http://localhost:5173.

SPA-serving Rust tests skip when `web/dist` has not been built; run `bun run build` first to exercise them locally.

CI (`.github/workflows/ci.yml`) runs the Rust lint job, a frontend job (frozen install, lint, format check, test, build), the test job — which consumes the frontend build output so SPA serving is tested for real — and the packaging job, which asserts the Homebrew tarball contract.

## Releases

Releases are cut manually: dispatch the `Release` workflow from the Actions tab with a `patch`, `minor`, or `major` bump.

1. `verify` runs every gate — Rust format, lints, tests, and the frontend's lint, format check, tests and build — and uploads `web/dist`, which every target build then embeds. Nothing is tagged until it passes.
2. `release` bumps the version with cargo-edit and pushes the commit and the `v<version>` tag.
3. `build` compiles one job per target in [`scripts/targets.json`](scripts/targets.json) — `darwin-arm64`, `darwin-x64`, `linux-x64` (Ubuntu), `linux-arm64` (native `ubuntu-24.04-arm`) and `win32-x64` — and runs `upland --version` on the binary it just built. Linux is statically linked against musl so an older glibc host can start it.
4. `package` writes one `upland-<version>-<target>.tar.gz` per Homebrew target (single member, mode `0755`, uid/gid 0, mtime at the epoch, so republishing hashes identically), `upland-<version>-win32-x64.exe`, and `SHA256SUMS`.
5. `github-release` publishes them.
6. `tap` dispatches `bump.yml` in [`xminihub/homebrew-tap`](https://github.com/xminihub/homebrew-tap) and waits for it: the tap checksums the assets, renders and gates `Formula/upland.rb`, and commits it. A release whose formula did not land is a red release.

The asset name is the contract between the two repositories. `scripts/asset-name.sh` derives every name from the target table, and the tap's `scripts/render.mjs` pins URLs built from the same pattern; a target the tap declares but this release does not publish fails the bump by name. See `CONTEXT.md`, `docs/adr/0001-distribution.md` and `docs/adr/0002-loopback-by-default.md`.

Packaging scripts need GNU tar (`brew install gnu-tar; TAR=gtar` on macOS) and run in CI's packaging job:

```sh
bash scripts/test-package-brew-tarball.sh      # the contract, asserted
bash scripts/asset-name.sh --version 0.1.1 --target linux-x64 --kind tarball
```
